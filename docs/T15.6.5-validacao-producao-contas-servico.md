## Estado

host antes de aplicar migrations ou habilitar qualquer feature flag.

- idempotência da confirmação sem criação de transação bancária;
- preservação da ocorrência seguinte e do valor-base da recorrência.

## Pré-condição administrativa pendente

O workflow usa `/usr/local/sbin/deploy-saldo360`, uma cópia privilegiada que não é substituída automaticamente pelo
release. Antes do próximo deploy, um administrador deve instalar a versão revisada:

```bash
sudo install -o root -g root -m 0755 \
  /caminho/do/repo/deploy/server/deploy-saldo360 \
  /usr/local/sbin/deploy-saldo360
```

O workflow agora compara SHA-256 da cópia instalada com o script do release e aborta antes do cutover quando eles
divergem. Não executar a validação financeira contornando esse bloqueio.

## Plano da janela controlada

1. Publicar um SHA Git completo e registrar a tag implantada.
2. Confirmar a aplicação das migrations `AddFinancialDocumentClassification`,
   `AddServiceBillOccurrenceConfirmations` e `AddServiceAccountBindings`.
3. Manter o scheduler Gmail desligado.
4. Habilitar classificação, extração, reconciliação, confirmação e binding; manter agentes desligados quando a
   extração determinística for suficiente.
5. Executar manualmente CEEE, DMAE e Vivo, um fornecedor por vez.
6. Revisar visualmente o documento antes de confirmar valor ou criar binding.
7. Reexecutar collector manual, previews, confirmação e binding para comprovar idempotência.
8. Conferir Agenda, projeção mensal, saldo projetado, pendências e timeline.
9. Encerrar a janela mantendo o scheduler desligado até decisão operacional separada.
