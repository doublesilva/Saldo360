# T08.1 — Diagnóstico do HTTP 409 no reset

Data: 21/10/2026. Investigação e correção mínima local de mensagem; sem repetir reset, executar exclusões,
chamar endpoints produtivos, mover arquivos, alterar flags, publicar ou deployar.

## Conclusão

**A rejeição é intencional: DocumentCutoverRequired.** Os cinco documentos do workspace afetado continuam
com StorageReference no layout familiar antigo. O guard exige o layout final correspondente ao workspace
e ao ID de cada documento. A migration financeira não converteu as referências físicas; essa preparação
continua sendo procedimento separado. O bloqueio não é, neste caso, disputa de concorrência.

**Resposta vazia não é o contrato.** O endpoint retorna HTTP 409 com JSON:

```json
{"code":"DocumentCutoverRequired"}
```

O frontend anterior ignorava o corpo de qualquer erro HTTP e substituía todo 409 por uma mensagem genérica
de orçamento alterado/indisponível. Isso ocultava o motivo real. Não havia leitura do JSON de erro.

## Rastreamento das condições de 409

| Origem | Condição | Corpo previsto | Posição/efeito |
|---|---|---|---|
| Serviço, Authorize | Tipo diferente de Personal | code=PersonalOnly | Antes das exclusões; owner validado primeiro. |
| Serviço, Authorize | Workspace inativo | code=WorkspaceInactive | Antes das exclusões. |
| Serviço, ResetAsync | Alguma referência difere do layout final exato | code=DocumentCutoverRequired | Após lock/revalidação, antes de inserir intenções, DELETEs e auditoria. É o caso produtivo. |
| FinancialWriteMiddleware | DbUpdateConcurrencyException, SQLSTATE 40001/40P01 ou P0001 com mensagem FINANCIAL_WORKSPACE_RESET_CONFLICT, inclusive encapsulados | code=FINANCIAL_WORKSPACE_CHANGED, message e traceId | Outro caminho; corpo JSON explícito e no-store. |

O endpoint captura FinancialResetRejected e devolve Results.Json com o code; NotFound é 404 e confirmação
inválida é 400. JSON inválido/extra, CSRF, tamanho e tipo de conteúdo produzem outros status, não este 409.

O handler global de exceções inesperadas produz 500 ou 503 via ProblemDetails; não cria um 409 vazio.
StatusCodePages não remove corpo já produzido. O nginx.conf revisado encaminha a API sem regra de interceptação
de erros que descarte esse JSON. A proteção de concorrência permanece ativa: época/versão do workspace,
lock PostgreSQL e triggers. Não foi removida, flexibilizada ou substituída para contornar a rejeição.

## Efeitos persistentes

**Nenhuma exclusão ou efeito financeiro do reset foi confirmado.** O guard está antes da primeira intenção
de cleanup e do primeiro DELETE. A exceção encerra a transação sem commit. A leitura mostrou ausência de
auditoria, de intenções e de época de reset, com os cadastros/documentos ainda presentes. Cleanup físico só
seria chamado após commit, caminho não atingido nesta rejeição.

Isso não equivale a afirmar ausência absoluta de qualquer escrita de infraestrutura: logs de acesso já
persistiram, e autenticação pode renovar sessão ou sincronizar nome antes do handler. Não existe snapshot
anterior dessas informações para provar ausência de tais atualizações nas tentativas históricas; não foram
lidos tickets/cookies para investigar isso. Nenhuma dessas rotinas é uma exclusão financeira do reset.

## Correção mínima e validação

Alterado somente o tratamento de erro no cliente: ler o code JSON de 409 e informar DocumentCutoverRequired,
PersonalOnly ou WorkspaceInactive com mensagens específicas. Corpo ausente/malformado/código desconhecido
mantém fallback seguro. Não exibe mensagem arbitrária do servidor, não faz retry automático e não registra
confirmação de sucesso. O backend, o guard, o formato de storage e os dados permanecem inalterados.

- Nove testes novos do parser compartilhado com fetch simulado, pelo caminho GET de preview.
- Frontend completo: **288/288 aprovados em 30 arquivos**; build aprovado.
- Lint sem erros, nove warnings preexistentes; diff --check sem erros.
- Nenhum teste backend/reset/DELETE ou migração foi executado nesta investigação.

Os testes frontend usam respostas simuladas; não fazem requisições reais ao reset produtivo.
Sem push ou deploy. A correção local esclarece o motivo, **não desbloqueia o reset**. Qualquer conversão dos
arquivos antigos exige autorização/procedimento próprios; não retirar o guard nem repetir a operação como
tentativa de resolver este caso.
