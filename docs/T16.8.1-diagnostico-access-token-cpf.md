## Momento dos eventos OIDC

Conferido o [handler ASP.NET Core 10.0.13](https://github.com/dotnet/aspnetcore/blob/v10.0.13/src/Security/Authentication/OpenIdConnect/src/OpenIdConnectHandler.cs),
versão referenciada pela aplicação. No Authorization Code configurado:

1. O código é resgatado e `OnTokenResponseReceived` recebe a resposta do token endpoint.
2. `OnTokenValidated` é executado com o ID token validado e `TokenEndpointResponse` disponível.
3. Após userinfo/filtro de claims, `OnTicketReceived` prepara a identidade e as properties do ticket.
4. O cookie handler grava o ticket protegido no store servidor; o navegador recebe só a referência.

Portanto, **não foi comprovado erro de timing no uso atual de `OnTokenValidated`**. Não movemos a
validação para um evento anterior à identidade validada nem passamos a usar `ProtocolMessage.AccessToken`
do callback do navegador. Os testes passam pelo handler completo, observam a ordem dos eventos e
decriptam apenas o ticket sintético depois da gravação para conferir seu conteúdo.

`SaveTokens=false` permanece. Somente o access token elegível é retido. ID token, refresh token e CPF
não entram no ticket. Uma sessão financeira válida pode existir sem token de perfil ou com token
expirado: agora essas condições têm códigos distintos, em vez de apenas `SessionInvalid`.

## Diagnóstico seguro implementado

`/api/me` preserva `cpfStatus` e acrescenta `cpfDiagnosticCode`, opcional e composto exclusivamente por
enum allowlisted. O tipo TypeScript aceita esse campo adicional, sem exibir ou armazenar CPF.
O código também acompanha o resultado interno e, para uma rejeição no callback, a metadata protegida
da sessão. Uma sessão antiga sem código não fabrica aprovação: informa `StoredAccessTokenMissing`.

| Etapa | Exemplos de códigos |
|---|---|
| Sessão | `SessionMissing`, `SessionAuthenticationFailed`, `SessionIdentityMismatch`, `StoredAccessTokenMissing` |
| Resposta/token | `AccessTokenMissing`, `BearerTokenTypeInvalid`, `AccessTokenMalformed`, `JwtTypeInvalid` |
| Validação criptográfica/documental do token | `AudienceMismatch`, `IssuerMismatch`, `SubjectMismatch`, `TokenExpired`, `TokenNotYetValid`, `TokenLifetimeInvalid`, `SigningKeyUnavailable`, `SignatureInvalid`, `AlgorithmInvalid` |
| Autorização do cliente | `ClientMismatch`, `SensitiveClaimsPresent` |
| Metadata/validador | `MetadataUnavailable`, `TokenValidationUnavailable` |
| Gateway | `GatewayUnauthorized`, `GatewayForbidden`, `GatewayUnavailable`, `GatewayTimeout`, `GatewayInvalidResponse`, `GatewayIdentityMismatch`, `GatewayCpfGrantMissing`, `GatewayCpfNotRegistered`, `GatewayCpfInvalid` |
| Êxito | `AccessTokenValidated` no callback; `ProfileAvailable` somente após o Gateway devolver CPF válido do próprio usuário |

Logs estruturados próprios:

- Evento 17080: `TokenResponseReceived` registra somente presença do access token e tipo Bearer como
  booleanos; `AccessTokenValidation` registra código/status fixos.
- Evento 17082: `TicketReceived` registra se o access token foi retido nas properties. Não é uma
  alegação de commit no banco; a gravação posterior é conferida pelos testes.
- Evento 17081: desfecho da consulta, com etapa, código e status, uma vez por instância scoped.

Nenhum desses eventos recebe objeto/mensagem de exceção, claims, valor de token, CPF, corpo do Gateway,
header, query ou identificador pessoal. A classe da exceção é usada apenas internamente para selecionar
um código fixo. Não foi reativado logging detalhado do middleware OIDC ou do cliente HTTP de perfil.

## Validações mantidas e correção restrita

Mantidos issuer exato, assinatura/JWKS RS256, `typ=at+jwt`, audience de perfil, expiração/nbf,
identidade ordinal igual ao ID token, tamanho limitado e recusa de claims CPF no access token.
O relógio/skew, TLS e as regras de autorização não foram flexibilizados.

Encontrada uma brecha independente no vínculo do cliente: anteriormente `client_id` correto fazia
um `azp` contraditório ser ignorado. Agora, quando ambos existem, ambos precisam corresponder ao cliente
configurado; duplicatas ou ausência dos dois continuam recusadas. `azp` sozinho válido e ambos iguais
continuam aceitos. Isso **não é apresentado como causa do `SessionInvalid` relatado**: essa contradição
produz `AccessDenied`/`ClientMismatch`.

O caminho `/api/me` do Gateway permanece fixo, sem parâmetros para escolher pessoa. O código local
do AccessGateway foi conferido: consulta CPF por issuer/subject do bearer validado e só lê/decifra
o atributo quando o cliente tem grant. Saldo360 confronta a identidade da resposta antes de usar CPF.
Ausência de grant, ausência de cadastro e resposta de outra identidade são estados diferentes.

## Limite e informação necessária para concluir o incidente

O fluxo válido demonstrou `cpfStatus=Available` e `cpfDiagnosticCode=ProfileAvailable` sem CPF no
JSON público. A configuração ativa não mostrou incompatibilidade de audience, algoritmo ou grant.
Entretanto, o binário ativo ainda é o anterior a estes diagnósticos. Sem executar deploy, não é
possível atribuir à sessão afetada um código novo nem afirmar que sua rejeição foi resolvida.

Após instalação pelo processo autorizado e nova autenticação, basta consultar `/api/me` e informar
**somente `cpfStatus` e `cpfDiagnosticCode`**. Não enviar cookie, ticket, token, CPF ou claims. Esses
dois campos distinguem a etapa que ainda falhar, evitando alterar emissor, assinatura ou autorização
para tentar obter sucesso. Caso indique `ProfileAvailable`, o critério operacional do CPF estará
comprovado; caso contrário, a correção deve ser aplicada à causa indicada, não presumida.

Nenhum push/deploy, migration, mudança de permissão ou alteração em coletores Gmail. Nenhuma chamada
OpenAI, obtenção de CPF real, fallback administrativo ou implementação financeira. A instrumentação
local está pronta; **o incidente real permanece pendente desse diagnóstico**, não homologado por
uma simulação nem declarado corrigido apenas porque os testes passaram.
