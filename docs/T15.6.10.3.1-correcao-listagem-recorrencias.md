# T15.6.10.3.1 — Correção da listagem de recorrências

## Diagnóstico reproduzido

Em PostgreSQL descartável, uma família existente com usuário Owner e nenhuma recorrência retornou HTTP 500 em ambos os GETs:

```http
GET /api/families/{familyId}/recurrences?includeArchived=true
GET /api/families/{familyId}/recurrences?includeArchived=false
```

Os dez casos iniciais de regressão falharam: dois de API e oito de acesso direto ao repositório. A consulta de participação retornou Owner e a consulta de entidades funcionou. A execução de `ListAsync` lançou `InvalidOperationException` na compilação da consulta pelo EF Core, antes de ler as linhas: a expressão `OrderBy(f => new RecurrenceDto(...).StartDate)` não pôde ser traduzida para SQL. Portanto, o erro também ocorre com tabela vazia e não depende de seed ou dados financeiros.

## Correção

- Filtro de família separado do filtro opcional `Status != Archived`, sem alterar sua semântica.
- Ordenação por `StartDate` e `Id` aplicada às entidades **antes** da projeção para o record posicional. Somente simplificar o predicado não corrige a expressão de ordenação não traduzível. Não há avaliação em memória nem alteração do DTO.
- `ApiExceptionHandler` passa a fornecer a exception ao logger, preservando stack trace e inner exceptions nos logs internos. Os metadados adicionais continuam restritos a código de erro, dependência, trace ID e caminho. Não foram adicionados headers, cookies, tokens, corpo, connection strings ou valores financeiros. O objeto de exceção pode conter detalhes técnicos da falha e deve permanecer em logs com acesso restrito.
- A resposta pública permanece genérica, com `INTERNAL_ERROR` e `traceId`, sem mensagem, tipo ou stack trace da exception; a classificação já existente de indisponibilidade PostgreSQL continua preservada.
- `RoutePattern: unmatched` decorria da limpeza do endpoint pelo pipeline de exceções. A observabilidade agora consulta também o endpoint original preservado em `IExceptionHandlerFeature`, sem registrar URL com query string ou outros dados da requisição.

## Testes direcionados

`FinancialRecurrenceListTests` cobre os dois GETs vazios com resposta exata `[]`, ausência de escrita financeira, participação Owner, tabela vazia, recorrência ativa, arquivada, combinação das duas, ambos os filtros, ordenação e isolamento de família no repositório.

`ApiExceptionHandlerTests` verifica retenção da exception/stack trace no logger, resposta sanitizada e ausência de metadados sensíveis da requisição. `RequestObservabilityMiddlewareTests` cobre o endpoint preservado após limpeza pelo pipeline de exceção. Os testes existentes de materialização também são executados como regressão relacionada.

Comando de validação (somente testes direcionados):

```powershell

git diff --check
```

Resultados locais:

- Antes da correção: 10/10 casos de listagem falharam, incluindo os dois GETs com HTTP 500.
- Depois da correção: 18/18 testes direcionados aprovados, zero falhas e zero ignorados (listagem, materialização, exception handler e observabilidade). Os testes de persistência/API utilizaram PostgreSQL 17 descartável.
- Após reforçar o teste de observabilidade para executar o pipeline real `UseExceptionHandler`, os seis testes de exception handler/observabilidade foram novamente executados: 6/6 aprovados. O corpo HTTP também foi verificado sem mensagem ou tipo da exception.
- `git diff --check`: aprovado; apenas avisos de conversão LF/CRLF do Git, sem erros de whitespace.
- Suíte geral e `npm run check` não executados, conforme o escopo de validação direcionada solicitado.
- Nenhuma migration criada ou alterada. A implementação ainda depende do fluxo de commit/CI/deploy e da validação autenticada em produção; esses passos não são declarados concluídos por este relatório.

## Produção e retomada

Nenhuma migration, alteração de dados produtivos ou execução de `saldo360ApprovedImport()` faz parte desta correção. Os registros dos testes são fictícios e ficam em PostgreSQL descartável.

A validação produtiva continua obrigatória após commit, CI verde e deploy do mesmo SHA. Na sessão autenticada e família previamente aprovada, executar somente os dois GETs acima e registrar status 200 e corpo `[]` (caso a família ainda esteja sem recorrências). Não considerar testes locais como prova de correção já implantada. Não retomar o executor de importação antes dessas evidências.
