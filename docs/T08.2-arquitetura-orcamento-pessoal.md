Implementação separadamente autorizada na T08.3: ver

Data da revisão: 20/10/2026. Estado: **arquitetura revisada proposta para aprovação explícita**.
Esta versão substitui a proposta anterior. Escopo exclusivamente documental: não implementa entidades,
migrations, endpoints, frontend, reset, conversão de dados ou storage. Não autoriza descarte de qualquer base.

## 1. Estado atual e problema

Hoje Family é o isolamento financeiro obrigatório. Os aggregates financeiros dependem de FamilyId e de serviços
que verificam participação familiar. A interface monta a área financeira dentro de Families.tsx.
FinancialBudget representa uma competência mensal com metas por categoria, não o contêiner global.
ServiceAccount e ServiceAccountIdentifier já pertencem ao usuário e permanecem separados.

O objetivo é operar sem Family, FamilyMember ou FamilyInvitation. Não criar família oculta, renomear FamilyId
ou transformar FinancialBudget na raiz. Como o produto está em concepção/MVP, não se justifica manter dois
modelos financeiros operacionais para preservar massa de desenvolvimento.

## 2. Decisões centrais

| Tema | Decisão proposta |
|---|---|
| Raiz financeira | **FinancialWorkspace**, com identificador próprio. |
| Modelo inicial | ApplicationUser → um Personal FinancialWorkspace → aggregates financeiros. |
| Multiplicidade | Exatamente um Personal por usuário provisionado; zero ou mais Shared apenas como extensão futura aprovada. |
| Tipos | Somente Personal e Shared; nenhum tipo transitório. |
| Ownership | OwnerUserId obrigatório no workspace; WorkspaceId é o escopo dos aggregates. |
| Família | Relação social opcional, fora do ownership financeiro pessoal. |
| Acesso pessoal | Somente owner lê, escreve, administra e poderá resetar; sem FamilyMember. |
| Shared | Fora do caminho crítico inicial; não habilitado funcionalmente enquanto suas regras não forem aprovadas. |
| Desenvolvimento | **Estratégia A: reset/reseed controlado**, somente de bases/conteúdos identificados e aprovados como descartáveis. |
| Dados importantes | Conversão pontual controlada, se a necessidade de preservação for confirmada; não criar arquitetura permanente para isso. |
| APIs/frontend | Migração direta para WorkspaceId, sem manter rotas financeiras familiares quando a nova versão estiver funcional. |
| FinancialBudget | Continua WorkspaceId + Competence + metas mensais; nunca raiz global. |
| ServiceAccount | Continua UserId; uso no workspace por vínculo autorizado quando necessário. |
| Reset T08.1 | Continua bloqueado até implementar o modelo pessoal e suas jornadas sem família. |

Não haverá mapa de identidade FamilyId→WorkspaceId em runtime, política financeira familiar de compatibilidade,
aliases financeiros, leituras/escritas duplicadas ou pontes de compatibilidade. A eventual atribuição de dados
em script pontual aprovado é procedimento de conversão, não relacionamento permanente do domínio.

## 3. Modelo alvo

Diagrama conceitual:

    ApplicationUser
      ├── exatamente 1 Personal FinancialWorkspace
      │     └── contas, categorias, movimentos, previsões, recorrências,
      │         metas mensais, cartões, dívidas, objetivos, cenários e documentos
      └── ServiceAccounts e identificadores pessoais

    Futuro, somente após regras aprovadas:
    ApplicationUser → zero ou mais Shared FinancialWorkspaces

    Family → relação social opcional entre usuários
             agregação/colaboração futura depende de autorização explícita

FinancialWorkspace mínimo:

| Campo | Regra |
|---|---|
| Id | ID independente de FamilyId, UserId e FinancialBudgetId. |
| OwnerUserId | Obrigatório, FK para ApplicationUser; nunca inferido de autoria dos registros. |
| Name | Nome de apresentação validado; não é chave de autorização. |
| Type | Personal ou Shared. |
| CreatedAt / UpdatedAt | Instantes UTC; não definem competência financeira. |
| IsActive | Estado operacional; inativar não apaga dados nem permite criar outro Personal. |
| Version | Concorrência de alterações administrativas. |

Unicidade por OwnerUserId filtrada por Type=Personal, **incluindo inativos**, impede dois pessoais.
O provisionamento garante sua existência quando o usuário entra na área financeira. “Exatamente um” resulta
do comando idempotente mais constraint; o índice sozinho garante apenas “no máximo um”.
Identidades ainda não provisionadas não precisam ganhar conteúdo financeiro em consultas de login.

Todos os aggregates terão WorkspaceId obrigatório; referências entre eles devem incluir o mesmo workspace
por FKs compostas. Conta, categoria, fatura, pagamento ou documento não podem cruzar workspaces por Id isolado.
Checks monetários, filtros de unicidade e idempotência continuam.

**CreatedByUserId ≠ OwnerUserId ≠ WorkspaceId.** Autoria/auditoria, titularidade e responsabilidade permanecem
conceitos próprios. Transferência de ownership não é um UPDATE genérico e não integra o escopo inicial.

## 4. Personal, multiplicidade e autorização

Fluxo alvo: login → ensure Personal → área financeira vazia → cadastrar conta/categoria.
Nenhuma operação pessoal depende de Family, FamilyMember ou FamilyInvitation.

Proposta de comando futuro: POST /api/me/financial-workspace, autenticado e com CSRF, chamado automaticamente
pela UI quando necessário. Repetições/concorrência retornam o mesmo Personal por unicidade transacional.
GET de preview, healthcheck e callback OIDC não devem criar workspaces como efeito colateral.

O workspace nasce sem contas, categorias, saldos, cartões, metas ou recorrências inventados.
Não recriar Personal para contornar inativação; eventual reativação precisa ser autorizada.
Sem família, o usuário deve conseguir todas as jornadas, não somente o futuro reset.

Para Personal:

- OwnerUserId é a única autoridade para ler, escrever, administrar e resetar.
- Receber WorkspaceId não é autorização; toda consulta/comando verifica o usuário autenticado.
- FamilyMember não é requisito nem alternativa permissiva de autorização.
- Dinheiro permanece decimal no backend/string exata no REST; CSRF e validação server-side permanecem.

Shared é extensão futura, com owner obrigatório. Não implementar ACL completa para liberar Personal.
Enquanto suas regras não estiverem aprovadas, criação/ativação de Shared deve ser recusada no backend e ausente
na UI; esconder o botão sozinho não basta. Compartilhamento e grants são requisitos futuros explícitos.

## 5. Family opcional/social

Family agrupa usuários. Sua existência, memberships e convites são independentes das finanças pessoais.
Criar/remover participação familiar não cria, transfere, expõe ou apaga entidades de Personal.

No futuro, Family poderá agregar indicadores autorizados ou associar Shared. Recomendação conceitual para
essa associação: Family com zero ou mais Shared; cada Shared associado a no máximo uma Family, sem relação
muitos-para-muitos desnecessária. Isso não precisa ser persistido nesta mudança inicial.
Personal não recebe FamilyId. Agregação não significa acesso a documentos/transações dos demais membros.

Não há política especial para família com um membro. O número de membros não determina ownership ou autoriza
conversão automática. Se houver dados importantes, o destino precisa ser aprovado independentemente dessa composição.

### Responsável e titular

ResponsibleMemberId da conta hoje aponta para FamilyMember. No alvo, usar responsabilidade opcional por UserId,
sem confundir com ownership. No Personal, não exigir família para montar opções do formulário.
Conversão pontual resolve o usuário pelo vínculo existente e exige revisão de inconsistências; não toma
essa referência como proprietário de todo o conjunto financeiro.

HolderUserId do cartão já é UserId, mas sua FK exige membership familiar. Retirar essa dependência financeira
preservando identidade do titular e regras de escolha aprovadas. Titular não recebe acesso automaticamente.
Se histórico importante não couber nas regras pessoais, interromper sua conversão e decidir o destino,
sem apagar informações nem habilitar Shared para contornar a incompatibilidade.

## 7. ServiceAccount pessoal

ServiceAccount e identificadores continuam UserId, fora do reset de W. A API /api/me/service-accounts mantém
seu significado pessoal. Resolver um documento não concede acesso irrestrito a esse cadastro.

Quando necessário, um vínculo autorizado permite usar a conta de serviço numa recorrência/documento sem
mudar owner. No Personal, validar propriedade/autorização da ServiceAccount; conhecer UC ou Id não prova permissão.
Uso por terceiro/Shared exigirá consentimento específico futuro. Não buscar identificadores globalmente entre
usuários nem duplicar valores protegidos dentro de W. Vínculos financeiros são resetáveis; cadastro pessoal,
identificadores e chaves não são.

## 8. Destinação dos dados e gate produtivo

### Desenvolvimento: estratégia A escolhida

Para massa **confirmada como descartável**, preferir reset/reseed controlado do contexto financeiro e fixtures
no schema final. Não manter complexidade de runtime para preservar contas/cartões/documentos fictícios.
Recriar massa de teste é aceitável; inventar fatos financeiros pessoais não é.

O reset/reseed técnico de desenvolvimento não é o reset funcional T08.1. A implementação deve identificar
base/storage exatos, verificar isolamento e obter autorização para os alvos. Não apagar usuários, sessões,
chaves ou conteúdo de outro ambiente por consequência de limpeza financeira.
Uma base inteira só poderá ser recriada se todo seu conteúdo tiver descarte explicitamente autorizado;
isso não é pressuposto desta arquitetura. Não usar caminhos amplos ou exclusões sem alvo validado.

### Produção: não presumir descartabilidade

Produção não foi consultada nesta revisão. O histórico contém relatos de cadastros manuais e documentos reais
produtivos; portanto **não está confirmado que inexista dado importante**. Estágio MVP não autoriza apagá-los.

Antes da implementação/corte, confirmar com o responsável:

1. Quais bases/arquivos são desenvolvimento/teste e podem ser descartados.
2. Se há dados produtivos/manuais a preservar e quais são, sem conteúdo sensível no Git.
3. Quem aprova descarte/conversão e qual usuário/workspace recebe cada conjunto preservado.

Se não houver dados relevantes, aplicar a estratégia direta aprovada. Se houver, executar **script pontual
de conversão controlada**, não um mecanismo permanente do domínio. Não atribuir dados por CreatedByUserId
nem pelo único membro atual. Conjuntos ligados por saldos/contas/faturas/pagamentos não podem ser separados
arbitrariamente. Destino ambíguo bloqueia conversão, sem duplicar dados em usuários diferentes.
Nenhuma decisão de descarte produtivo foi tomada nesta revisão.

## 9. Sequência curta de implementação — não executada

Planejar release coordenada, ensaiada localmente, com janela de manutenção se necessário.
Não exigir operação simultânea de versões com escopos diferentes nem prometer zero downtime.
As fases organizam a mudança; não são versões intermediárias de compatibilidade em produção.

| Fase | Alteração planejada | Integridade/autorização | Retorno seguro |
|---|---|---|---|
| 1 — raiz | Criar FinancialWorkspace e ensure Personal para usuários aplicáveis. | Owner obrigatório, tipos Personal/Shared, unicidade do Personal; Shared desabilitado. | Em falha antes do corte, manter aplicação/dados atuais intactos. |
| 2 — escopo | Preparar W e referências/índices dos aggregates. | Constraints por W e checks monetários preservados; colunas temporárias somente se necessárias ao procedimento offline. | Corrigir ensaio antes do corte, sem descartar dados importantes. |
| 3 — dados | Descartar/recriar apenas massa autorizada ou converter pontualmente dados importantes. | Destino inequívoco; conferir IDs, fatos, vínculos, arquivos e idempotência; sem writers concorrentes. | Falha de conversão de banco provoca rollback; originais de arquivos preservados até validar. Descarte não é reversível sem cópia. |
| 4 — aplicação | Alterar serviços/repos/APIs/frontend/coletores diretamente para W. | Owner do Personal, sem FamilyMember; todos os comandos e caminhos de origem isolados por W. | Não reabrir tráfego antes de validar a entrega completa e o plano de recuperação. |
| 5 — schema final | Retirar FamilyId financeiro e suas FKs/índices substituídos; W obrigatório. | Somente W como escopo; Family social preservada; validar FKs/uniques. | Não tratar migration Down destrutiva como retorno cotidiano; recuperar conjunto coerente sob plano aprovado. |
| 6 — desacoplamento | Retirar dependências financeiras de FamilyMember em responsável/titular/DTOs/configurações/testes/UI; provar jornadas sem família. | Nenhuma dependência familiar oculta, inclusive em importações e scheduler configurado. | Qualquer dependência restante bloqueia liberação; corrigir e repetir ensaio. |

As dependências podem exigir executar a fase 6 junto à 4/5; a numeração não autoriza liberar versão quebrada.
Na base final não ficam FamilyId financeiro ou duas fontes de ownership.
Não reescrever casualmente migrations históricas existentes: migrations diretas ou baseline de ambiente
descartável serão decididos na implementação conforme os ambientes efetivamente aprovados.

### Integridade

Revisar todas as FKs e unicidades reais: W/competência dos orçamentos mensais; referências a categorias;
W/recorrência/número das materializações; OperationId dos pagamentos/alocações conforme índices existentes;
W/hash e W/source/external-id da Inbox com filtros preservados; lote/compra/parcela/fatura; bindings/checkpoints.
Não substituir regras por CASCADE indiscriminado.

Se houver conversão importante, preservar IDs, valores/datas/estados, saldos de referência, OperationIds,
vínculos e evidências. Comparar contagens/fingerprints e projeções T06.3/T07.3/T07.5 com a mesma data-base
São Paulo, snapshot e filtros. Não recalcular fatos, reconstruir compras ou rematerializar recorrências.
Verificações detalhadas ficam em ambiente protegido, sem dados pessoais em logs/commits.

### Rollback operacional

Preparar backup/restauração coerente de banco e documentos importantes antes do corte. Com tráfego bloqueado,
uma falha permite abortar e recuperar o conjunto previamente ensaiado. Depois de aceitar novas escritas,
preferir correção ou release compatível com W: restaurar snapshot anterior pode perder escritas posteriores
e exige decisão operacional explícita sobre RPO/reconciliação. Não manter a aplicação anterior como arquitetura
permanente para prometer retorno sem risco.

## 12. Storage

Layout final de novos documentos: workspaces/{workspaceId:N}/{documentId:N}.pdf.
Autorização é pela entidade documental em W, não pelo path. Manter validação dentro da raiz e referências seguras.

Para arquivos descartáveis de desenvolvimento, limpar/reimportar somente sob autorização e testar no layout
final. Não criar camada permanente de resolução de dois layouts para massa descartável.
Se houver arquivo importante, o script pontual copia para o layout final, verifica bytes/hash/tamanho,
atualiza StorageReference e valida leitura antes de remover original sem referências.
A versão final utiliza o layout final; falha na preparação mantém original recuperável.
Não existe transação distribuída entre PostgreSQL e filesystem. Cleanup/conversão pendente bloqueia liberar
o conjunto afetado. Nenhum arquivo foi movido ou apagado nesta revisão.

## 13. Gmail e checkpoints

Checkpoint financeiro passa a W/configuração estável da coleta, sem FamilyId paralelo.
ProfileName não basta para misturar mailboxes diferentes. Credenciais, tokens e consentimento permanecem
globais/pessoais conforme a configuração existente, separados do destino financeiro.

Para massa descartável, progresso pode ser reiniciado explicitamente, sabendo que a coleta poderá reencontrar
documentos. Para dados preservados, o script pontual mantém watermark/dedupe quando necessário.
Não avançar progresso como efeito de conversão nem mudar a identidade externa dos anexos.
Scheduler e coleta manual precisam ser configurados/validados por W antes de voltar a operar;
não habilitá-los automaticamente. Esta revisão não retoma T15 nem executa coleta.
